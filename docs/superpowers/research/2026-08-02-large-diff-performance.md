# Handling 20k-line diffs

**Status:** research, no decisions made
**Measured against:** livediff 0.6.0, Node 22.14, macOS
**Reproduce:** `bench/` — see Appendix

Every number here is measured, not estimated, except where marked. The headline finding is that
**the biggest problem is not the UI**, so the cheapest fixes are also the safest ones.

## Summary

| Finding | Impact |
| --- | --- |
| `getDiff` spawns `git diff` once per file, sequentially | 500 files takes **7.3s**; one whole-tree spawn takes **75ms** |
| Diff parsing is cheap | 20k lines parses in **112ms** — not worth optimizing |
| DOM node count is the real rendering wall | **≥140,000 nodes** for a 20k-line split view |
| The diff library already sets `content-visibility: auto` | Off-screen rows already skip rendering |
| WebKit's `content-visibility` is broken for find-in-page | **Cmd+F may already be broken in Safari today** |
| A diff change triggers a full refetch and full reparse | No debounce, no cancellation, every file re-parses |

## What was measured

Five diff shapes, each ~20k changed lines, chosen because they stress different parts of the
pipeline. Fixtures are generated by `bench/gen.mjs`.

| Shape | `getDiff` | Files | JSON payload | Why it matters |
| --- | --- | --- | --- | --- |
| One huge file (generated client) | 121 ms | 1 | 1.60 MB | Worst case for the renderer, best for the server |
| 500 small files (codemod sweep) | **13,864 ms** | 500 | 1.68 MB | Worst case for the server |
| 40 modified files × 500 lines | 719 ms | 40 | 1.74 MB | The realistic middle |
| Minified bundle (one line) | 117 ms | 1 | 0.25 MB | Pathological line length |
| Lockfile (20k lines) | 120 ms | 1 | 1.38 MB | Common, and nobody wants to read it |

The payload is ~1.6 MB regardless of shape, which is fine over localhost. **File count, not line
count, is what hurts today.**

### The server is the dominant cost, and it is an easy fix

`getDiff` loops `for (const [path, stat] of numstat)` and awaits a separate `git diff HEAD -- <path>`
inside the loop (`server/git.js:131-136`). That is one process spawn per file, in series.

Measured on 500 modified files (`bench/spawn-strategy.mjs`):

| Strategy | Time | Speedup |
| --- | --- | --- |
| Sequential per-file spawn (today) | 7,341 ms | 1× |
| Concurrent per-file spawn, 16 at a time | 1,137 ms | 6.5× |
| **One whole-tree `git diff`, split in JS** | **75 ms** | **98×** |

Splitting one `git diff HEAD` on `/^diff --git /m` produced exactly the same 500 chunks. Git is
optimized for this; we were fighting it.

Two caveats before implementing: the split must preserve the `diff --git` prefix it splits on, and
rename/binary/mode-change headers need checking against the current `buildFile` parser. Untracked
files still need their own `--no-index` pass, but that loop can be concurrent.

### Parsing is not the problem

`@git-diff-view/core` on a 20k-line tracked diff (30,006 patch lines, 2.4 MB):

- `buildSplitDiffLines()` — **112 ms** → 20,000 rows
- `buildUnifiedDiffLines()` — **74 ms** → 30,000 rows

Two decisions follow. A web worker for parsing would add real complexity to save ~100ms, so it is
not worth it. And **unified mode produces more rows than split** (30k vs 20k) — split pairs
additions with deletions on one row. Split is the cheaper mode here, which is counterintuitive.

### DOM node count is the wall

`bench/dom-nodes.mjs` counts what the browser must build:

| Mode | Rows | DOM nodes (floor) |
| --- | --- | --- |
| Split | 20,000 | **≥140,000** |
| Unified | 30,000 | **≥180,000** |

**These are floors.** The probe's token-tree sampling returned zero (the syntax API differs from
what it guessed), so the count covers only the `<tr>`, its cells, and one wrapper — it excludes
every syntax-highlighting `<span>`. `diffViewHighlight` is on in `FileDiff.jsx:61`, so real counts
are plausibly 2–3× higher. Getting an exact number needs a real browser; see Open Questions.

For scale, a page starts feeling heavy around 10–15k nodes. This is an order of magnitude past
that, and it is why the answer cannot be "just render it faster".

## Cmd+F: the real constraint

This is the decision that shapes everything else.

**The library already ships `content-visibility: auto` on every `tr`**
(`node_modules/@git-diff-view/react/dist/css/diff-view.css`), and `src/main.jsx:3` imports that
stylesheet. So off-screen rows already skip layout and paint today. That is why livediff is
tolerable on medium diffs.

What that buys, and what it costs:

- **Chrome/Edge:** content stays findable. The engine renders a skipped subtree when a find hits
  it, then scrolls there. Cmd+F works.
- **Safari/WebKit:** the implementation is **broken for find-in-page**. Text in skipped subtrees
  is not reliably found.
- **Firefox:** works from 125 onward; earlier versions needed a flag.

**This means Cmd+F is probably already broken in Safari for any diff taller than the viewport.**
Nobody has tested it. That is the single most valuable thing to check when you are back, and it is
a 60-second test — see Open Questions.

The library also sets **no `contain-intrinsic-size`**. Without it, skipped rows are measured as
zero height until scrolled into view, so the scrollbar is wrong and jumps as you scroll. On a 20k
diff that is not cosmetic — it makes the scrollbar useless for navigation.

### The virtualization tradeoff

Virtualization removes off-screen rows from the DOM entirely. That fixes node count completely —
and **breaks Cmd+F in every browser**, not just Safari, because the text genuinely is not there.

Every project that virtualizes ends up rebuilding find: search the underlying data, compute the
row index, `scrollToIndex`, then highlight. That is real work, and it will never feel native —
no match count in the browser chrome, no Enter-to-cycle, different keybinding unless you hijack
Cmd+F (which browsers allow but users often resent).

So the honest framing is a fork, not a ladder:

| | Keep `content-visibility` | Virtualize |
| --- | --- | --- |
| DOM nodes | All present (≥140k) | ~50 rows |
| Cmd+F | Works in Chrome, broken in Safari | Broken everywhere; needs a custom UI |
| Memory | High | Low |
| Scroll accuracy | Needs `contain-intrinsic-size` | Exact |
| Work to implement | Add one CSS property | Rewrite `FileDiff` around a virtualizer |
| Risk to comments/widgets | None | High — inline comment threads are variable-height rows |

The comment threads are the part I would worry about most. `renderExtendLine` injects a
variable-height React tree into arbitrary rows. Virtualizers handle dynamic heights, but the
measurement churn on a 20k-row list with a dozen expanded threads is exactly where these
integrations get fragile.

## The option nobody has priced: don't render it

GitLab caps diffs rather than optimizing them — **200 KB per patch, 1,000 files, 50,000 lines**,
with files over 10 KB collapsed behind a "Load Diff" button. GitHub does the same with "Load diff"
and "This file has been truncated".

This is worth taking seriously because it is *less* work than virtualization and it targets the
actual complaint. Nobody reads 20,000 lines. They read the 200 lines they care about and skim a
file list. Collapsing large files by default:

- keeps every row out of the DOM until asked for, like virtualization
- preserves Cmd+F semantics exactly (expanded content is fully in the DOM)
- needs no new library and no changes to comment rendering
- gives an obvious place to put "this is a lockfile, you don't want this"

The cost is a click, and the risk is that a collapsed file hides a comment. That last part
interacts with the v0.6 lifecycle work: a comment on a collapsed file is still live and still
counted in the rail, so it must be surfaced — probably by auto-expanding any file with open
comments, which is also just the right default.

## Interactions with what already exists

**The `dir` filter added in 0.6 is already a mitigation.** `livediff apps/expo` scopes the render
to one subtree, which is exactly the "don't render 20k lines" answer arrived at from a different
direction. It is worth measuring how far that alone gets us on a real monorepo diff.

**The live-update path compounds every cost above.** In `App.jsx:122-128`, an `onDiff` event
triggers `loadDiff` for the whole workspace. There is no debounce, and `setDiff` installs a new
object, so the `useMemo(..., [file])` in `FileDiff.jsx:16` invalidates for *every* file and every
`DiffView` re-parses. On the 500-file fixture that is 7.3s of server work plus a full client
reparse — per save. The poll ticks every second, so saves during an edit queue up behind each
other. There is also no request cancellation, so responses can land out of order and show a stale
diff.

Fixing the refetch is independent of any rendering decision and probably matters more day to day.

**Syntax highlighting is on for everything.** `diffViewHighlight` (`FileDiff.jsx:61`) uses
lowlight/highlight.js. Highlighting a 20k-line lockfile is pure waste. A length threshold per file
would be a small, safe win.

## Suggested order

Ordered by value per unit of risk, not by size.

**1. Single whole-tree `git diff`** — 98× on the worst shape, server-only, fully covered by
existing tests. No UI risk at all. This is the obvious first move.

**2. Debounce + cancel the diff refetch** — stops the compounding. Also server-independent.

**3. `contain-intrinsic-size` on rows** — one CSS property; makes the `content-visibility` already
shipping actually work properly, and fixes the scrollbar.

**4. Collapse large files behind "Load diff"** — the GitLab pattern. Auto-expand files with open
comments. This is where I would stop, and I suspect it is enough.

**5. Virtualization + custom search** — only if 4 proves insufficient. It is the only option that
requires giving up native Cmd+F, so it should be last and should be a deliberate decision, not a
default.

## Outcome (2026-08-03)

Decisions taken: Safari does not matter, native Cmd+F is not required, both diff shapes must work,
and lockfiles are a separate concern. That unblocked virtualization, so items 1, 2 and 5 were
built and 3 and 4 were skipped — `content-visibility` and collapse-by-default both become moot
once rows are not in the DOM at all.

**Server (shipped, 0.6.0).** One whole-tree `git diff` split by path, with a per-file fallback;
untracked files synthesized from a read rather than two `--no-index` spawns each.

| Case | Before | After | |
| --- | --- | --- | --- |
| 500 untracked files | 13,864 ms | 137 ms | 101× |
| 500 tracked modified | 7,341 ms | 311 ms | 23× |

**Renderer (behind `RENDERER`, default `classic`).** Flat row model with analytic monospace
heights. Measured on the 20k-line fixture:

| | |
| --- | --- |
| Rows | 20,002 |
| Document height | 400,066 px, computed in 4 ms |
| Rendered at scroll 250,000 px | **62 rows** |
| Window selection | 0.081 ms |
| Search over every row | 8 ms, 10,000 hits |

Against the ≥140,000 DOM node floor measured above, that is roughly 400 nodes — about 320× fewer.

Two follow-ups this opens rather than closes:

- **Shiki becomes affordable.** Highlighting ~60 visible rows instead of 20,000 changes the
  economics; a heavier, better highlighter is now the cheaper option. See
  `2026-08-03-related-projects.md`.
- **The refetch is still undebounced.** Item 2 above was addressed only by `useScrollAnchor`
  preserving scroll position, not by reducing the work. On a large diff every save still refetches
  and rebuilds everything.

## Open questions for you

1. **Does Cmd+F work in Safari on a long diff today?** Open a diff taller than the viewport in
   Safari, search for text near the bottom. If it fails, that is a live bug in 0.6, independent of
   any of this work. Chrome should work.
2. **Is native Cmd+F worth keeping?** Everything above hinges on it. If you would accept an in-app
   search box with match counts and Enter-to-cycle, virtualization becomes attractive and the
   node-count problem disappears entirely.
3. **What is your real worst case?** The measured shapes are synthetic. A `pnpm-lock.yaml` change
   plus 30 source files is a very different problem from a 500-file codemod, and shapes 1 and 4
   above solve different halves of it.
4. **Should lockfiles and generated files be collapsed by name?** `*.lock`, `pnpm-lock.yaml`,
   `*.min.js`, `dist/**` are almost never read in review.
